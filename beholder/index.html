Introdução

Beholder observa processos no Linux e guarda o que viu. Memória residente, uso de CPU e — quando há uma NVIDIA na máquina — a VRAM de cada processo, tudo numa janela de tempo que você escolhe. A mesma máquina de estado atende o painel gráfico e o modo MCP, de modo que um agente enxerga exatamente o que você enxerga.

Regra de ouroCada timestamp vem da amostra real que produziu aquele máximo ou último valor. O Beholder nunca interpola: o que está no gráfico aconteceu.

Dois modos de leitura: Dev (imersivo, com a arte e o diagrama da troca MCP) e IA (ficha clara e densa, o mesmo texto sem enfeite). Use Copiar contexto para IA para levar o guia inteiro como Markdown.

Capacidades1. O que ele observa

Memória residente

RSS por processo, lido de VmRSS. O pico da janela fica sempre visível ao lado do valor corrente.

VRAM da NVIDIA

Memória da placa e por processo, via NVML em processo. Sem GPU, degrada para N/A sem derrubar nada.

Alvos flexíveis

Por PID, por nome exato (comm) ou por trecho da linha de comando completa.

Janela contínua

30 s, 5 min, 30 min ou 1 h. Acima de 1200 pontos, o buffer reduz por bucket sem inventar timestamps.

Modo MCP

JSON-RPC por stdin/stdout. Paridade integral com a GUI — mesma Model, mesma semântica.

Exportação

CSV achatado para planilha, JSON estruturado com séries separadas de RAM e VRAM.

Primeiros passos2. Compilar e executar

Compilação

cargo build --release
./target/release/beholder

Painel gráfico

O modo padrão. Adicione alvos pelo campo superior, escolha a janela e acompanhe as séries.

./beholder

Modo headless (MCP)

Sem janela. Lê requisições JSON-RPC de stdin e responde em stdout — o formato que um agente consome.

./beholder --mcp

Pacote Debian

./packaging/build-deb.sh
sudo apt install ./dist/beholder_*.deb
NotaO empacotamento exige dpkg-dev. Os ícones em packaging/icons/ são gerados a partir da arte do projeto e só precisam ser refeitos se ela mudar.

Vocabulário4. As métricas

MétricaO que é
RSSResident Set Size — a memória física que o processo ocupa na RAM neste instante. Vem de VmRSS.
CPU%Uso de CPU normalizado pelo número de núcleos.
VRAM TotalMemória total da placa (GPU 0).
VRAM UsedMemória em uso na placa inteira, não apenas pelo alvo.
VRAM FreeMemória de placa ainda disponível.
VRAM (proc.)Memória de GPU atribuída a um processo específico.
PicoO maior valor dentro da janela atual — não do histórico inteiro.

Amostragem5. Janela, intervalo e redução

O buffer guarda no máximo 1200 pontos por série. Quando a janela é longa demais para caber nesse teto, os pontos são agrupados em buckets.

SérieRedução por bucketRazão
RAMmaxO gráfico mostra o envelope de pico — é o que importa num vazamento.
VRAMmaxMesma lógica da RAM.
CPU%lastPico de CPU é ruído; o valor recente é o sinal.

O tamanho efetivo do bucket é max(intervalo_ms, janela_ms / 1200). Intervalos disponíveis: 100 ms, 250 ms, 500 ms, 1 s e 2 s.

GarantiaCada timestamp vem da amostra real que produziu aquele máximo ou último valor. Beholder nunca interpola — o que está no gráfico aconteceu.

Alvos7. Como escolher o que observar

Por PID

Direto ao ponto quando você já sabe o número. Reciclagem de PID é detectada pelo starttime do processo, então um PID reaproveitado não é confundido com a continuação do anterior.

Por nome exato

Casa com o comm — o nome curto, limitado a 15 caracteres no Linux. Adiciona todos os processos vivos com aquele nome de uma vez.

Por trecho da linha de comando

Busca na cmdline completa. É o que resolve quando o binário se chama node mas o que você quer é o processo que roda determinado script.

Limite conhecidoAlvos são resolvidos uma única vez, no momento do pedido. Processos que nascem depois com o mesmo nome não entram sozinhos — não há re-varredura.

Forma9. Arquitetura

Um binário, um processo do sistema operacional. Nenhum sidecar em outra linguagem, nenhum HTTP entre as partes.

CamadaResponsabilidade
crates/coreAmostragem, buffer em anel, máquina de estado. Sem nenhuma dependência de UI.
crates/appCasca egui. Apenas View e despacho de Msg — nenhuma lógica de domínio.
FluxoElm-style unidirecional: Msg → update → Model → View.
NVMLEm processo, nunca por CLI. Latência baixa e ausência tratada com elegância.

As especificações em docs/00-brief.md até docs/06-discretion.md são canônicas: valem mais do que o que o código porventura esteja fazendo.

Exemplo de troca11. Requisição e resposta

  1. stdinget_liveAgente → Beholder

    Uma requisição JSON-RPC por stdin, com o binário em ./beholder --mcp.

    { "jsonrpc": "2.0", "id": 1, "method": "get_live", "params": {} }
  2. stdoutBeholder → Agente

    A amostra corrente de cada alvo, RAM e VRAM.

    {
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "timestamp_ms": 1697125200000,
    "samples": [
      { "pid": 1234, "name": "python3",
        "rss_bytes": 524288000, "cpu_pct": 25.5, "vram_bytes": 1073741824 },
      { "pid": 5678, "name": "cargo",
        "rss_bytes": 804453376, "cpu_pct": 0.0,  "vram_bytes": null }
    ]
  }
}
  3. nullem Agente

    vram_bytes: null significa uma de duas coisas: não há NVIDIA disponível, ou o processo não reservou memória de GPU.

  4. stdinhealthAgente → Beholder

    Use health para distinguir os dois casos: ele devolve versão, estado do sampler, disponibilidade de NVML e config.

    { "jsonrpc": "2.0", "id": 2, "method": "health", "params": {} }
